# TheoremOS 首轮真实用户试用

本文件是可直接使用的试用材料。2026-11-07 确认暂时没有试用者，真人试用尚未执行。现有自动化测试、维护者真实模型验收和模拟运行不计入这里的结果；下表与模板保持待填状态。

入口：[工作台](https://app.theoremos.top/) · [使用说明](https://app.theoremos.top/guide.html) · [部署与运维](web-operations.md)。开始前记录实际部署提交号，不能用开发分支的测试结果替代线上版本。

2026-11-08 已整理离线 `trial-kit.zip`，本机位置和版本边界见[发布状态](web-release-status.md)。`participant/` 只含任务卡、反馈表与三份结果；`facilitator/` 保存判定答案、观察表及来源。只把参与者目录交给参与者，主持人答案在其自行解释后核对。A 复用维护者真实验收与下载包；B / C 复用现有失败 runner 生成并标记为 fixture，耗时和用量不计入真实产品统计。静态图片可检查结果理解，但不能证明能在在线界面找到或操作按钮；相关步骤仍需现场观察。

首轮找 5–10 位从未使用过 TheoremOS 的参与者。前 5 位建议包括 3 位有数学背景、不会或很少使用 Lean 的人，以及 2 位 Lean 使用者；先修复反复出现的阻塞，再用另外 3–5 位新参与者复核。记录每人的背景，不把两组的上手时间混为一个平均数。

每人预留 30–45 分钟。参与者自行使用有权限的邮箱和模型账户；主持人提前与参与者确定本次调用预算。记录服务商、模型和用量，不收集或复制 API Key。若不愿调用付费模型，仍可完成入口和结果理解任务，但要把真实提交一项标为未执行。

主持人先准备当前版本的三份只读结果：完整验收通过、达到时间或 Token 上限、Key/网络/环境导致运行失败。可以使用有明确 fixture 标记的本地演练环境；模型失败和超预算场景不必通过反复付费调用制造。模拟结果只用于检查理解，不能作为产品实际解题成功率或真实耗时。

每次只给参与者一张任务卡，先不展示观察表或按钮位置。请参与者边操作边说出自己的判断。卡住时先问“你现在想完成什么、正在找什么”，记录原话；确需帮助时写下提示内容，并将该步标为“提示后完成”，不能计为独立完成。

| 任务卡 | 给参与者的原话 | 主持人记录的完成证据 |
| --- | --- | --- |
| A：认识与进入 | “从官网开始，告诉我这个产品适合谁、你输入什么、最后会得到什么。然后进入你能开始工作的地方。” | 是否理解输入与交付；首次选择的入口；是否误以为任意自然语言结论都有正确性保证 |
| B：建立账号与连接 | “建立你自己的账号，选择本次要使用的模型连接。发送前说明费用由谁承担，以及你愿意花多少时间和模型用量。” | 邮箱登录成功；找得到 Key/模型设置；能区分平台次数额度、Token 用量与服务商金额；无需主持人代填 |
| C：做一次小任务 | “证明：对任意自然数 n，都有 n + 0 = n。请提交这道题，并在运行中解释你看到的进展。” | 自然语言原题完整；实际运行 ID；首次提交与首条进展时间；模型审核和证明阶段是否可区分 |
| D：离开与回来 | “先记住这次研究，刷新或离开页面再回来，找到同一次研究并判断它是否还在执行。” | 找回原运行，未重复创建；队列、执行、中断等状态判断正确；草稿是否保留 |
| E：理解交付 | “查看这份完成结果，说明哪里保证了什么、哪些判断还需要你核对。把你以后复核需要的材料保存下来。” | 找到源码、验收报告或复核包；区分 Lean 证明验收与自然语言陈述忠实性；下载文件可以识别 |
| F：理解未完成 | “分别看这两份结果：一份预算用完，一份运行失败。说明是否证明了命题、可能原因，以及你会如何继续。” | 不把超预算解释为命题为假；不把运行失败当成数学反例；下一步针对费用、Key、网络或环境，知道重试可能产生新费用 |
| G：自己的题目 | “选一道你确实关心的小问题，写出你会提交的内容，并说明本产品在哪一步最有用。” | 原题是否含变量、假设与目标；是否愿意再次使用；尚缺的关键能力。第二次真实调用可不执行 |

任务 C 开始前展示当前产品默认上限：形式化最多 10 分钟 / 400,000 Token，后续证明最多 5 分钟 / 5 轮 / 200,000 Token。参与者确认后再提交，也可选择更低上限或仅完成只读任务；缩小预算可能无法完成这道题。记录实际设置与两阶段分别报告的用量，不把上限写成实际花费。环境准备和最终验收可能增加墙钟时间；用量上限依赖服务商报告，进行中的请求可能超出，金额上限以服务商账户设置为准。

Lean 使用者可另做直接输入任务：`theorem add_zero_trial (n : Nat) : n + 0 = n := by sorry`，选择匹配的 Lean 环境。它检查进阶入口的易用性；自然语言路径与 Lean 路径的首次成功时间分开统计。

成功、超预算和运行失败的理解按下表判定。请先让参与者自行解释，再核对，不要提前朗读答案。

| 结果 | 合格理解 | 需记录的误解 |
| --- | --- | --- |
| 完整原题通过 | 冻结 Lean 声明下的全部目标通过独立验收；自然语言转写是否忠实仍看单独的陈述审核与人工判断 | “模型说完成就算证明”“编译通过就保证自然语言翻译正确” |
| 时间 / Token 用完 | 在本次预算内尚未完成；已有候选或局部检查不能替代完整验收 | “证明命题是假的”“失败所以肯定没有模型费用” |
| 运行失败 | 连接、Key、限流或运行环境等问题阻止流程，须依据具体原因处理 | “Lean 已经否定了原题”“反复点提交不会增加任务或费用” |

建议第一批的放量条件：至少 4/5 人无需提示完成登录、连接和首次提交；全部参与者能区分完整验收、超预算与运行故障；至少 4/5 人能找到复核材料；没有重复出现且未修复的核心流程阻塞。未达到时先修最常见的阻塞，再找新的首次使用者复核。这些是待验证的产品目标，当前尚无真人结果。
