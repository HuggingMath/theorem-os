# Skill research mode

This branch separates pinned Skill research methods from execution and coordination. A native agent harness executes research and tools; a project skill supplies methods. The host keeps the frozen problem, source policy, resource accounting, writer shutdown, independent Lean acceptance and persistent artifacts. Skill methods work in single, independent and cooperative runs through Codex, Claude Code, OpenCode or a configured headless CLI; see [harness configuration and verified limits](harness-portability.md).

## Start and resume

Build the runtime normally with `bun run build --state-root EXTERNAL_BUILD_DIRECTORY`. Use its manifest when preparing a **new** isolated run:

```sh
bun bin/math.ts run --research-mode skill \
  --workspace NEW_PROBLEM_WORKSPACE --task-file TASK_FILE \
  --output NEW_RESULT_FILE --build-manifest BUILD_MANIFEST
```

New `--research-mode skill` runs default to one independent researcher. Explicit `--workers` above 1 defaults to cooperative coordination; explicit `--coordination cooperative` defaults to 4 workers. Independent attempts remain selectable. Schedulers, module plans and plan approval retain their existing contracts. Cooperative Skill runs keep the complete task graph, ownership, typed delivery, fixed Reviewer and integration loop. All existing budget options apply; their unlimited defaults are preserved. New Skill runs use the existing library application and task automation where applicable, checked through the original acceptance path.

The normal `--resume` command inherits the saved research mode, skill loading, workers and coordination. It continues the saved native thread when the frozen contract permits. Mode, skill content, loading mode, provider, environment and other frozen identities cannot be changed in place. New runs save `researchSkillWorkflow: full` and an execution plan. Historical Skill checkpoints without that marker keep their original single-only workflow; resume does not silently upgrade their strategy. A different strategy starts a new run and thread from saved artifacts.

The default `--skill-loading native` checks Codex discovery and sends native skill input on ordinary host turns. `--skill-loading file` explicitly directs Codex to read the same pinned file. Native child communication carries the host's frozen context and explicit pinned-file reading instructions; its execution plan records file loading because Codex's typed input cannot combine an inter-agent communication with a skill input. Discovery and an accepted request do not prove that a provider followed the skill; that requires separate execution evidence.

## Codex adapter boundary

The adapter uses Codex's native shell, process polling, patches, tool-error feedback, Skill loading, thread resume and compaction. Shell settings are supplied once in the thread's developer instructions. Rejected arguments return through Codex's own tool output; the host no longer polls rollout files, counts refusals or injects duplicate corrections into later turns.

Ordinary declaration lookup uses native shell `rg` over the saved declaration index and source files. The host still generates the index and preserves frozen package identities. Catalog operations remain available for dependency metadata and archived evidence; the historical declaration-search CLI remains compatible with saved Skill instructions.

File handoffs use native `fs/watch` on the existing parent directory before the writer starts, `fs/changed` notifications and `fs/unwatch` during cleanup. There is no host polling timer. Codex 0.169.0 debounces watch events by 200ms and may fall back to a noop watcher; request admission and terminal completion therefore still read the output synchronously. Already validated output is checked by digest after the turn settles so a validator with submission side effects is not invoked twice. Content validation and independent proof acceptance stay with the host.

New Codex report workflows prefer native `outputSchema` and the final response bound to the completed turn. The host closes the session, validates the response and saves the frozen output file. `outputDelivery` freezes this choice; older requests without the field retain their file protocol and instruction hashes. Replay, other harnesses, the DeepSeek/Westlake Chat bridge and early proof handoffs retain file delivery. The audit reads the session's final-response record instead of collecting a second copy of agent messages.

The legacy non-Skill research path uses native `thread/compact/start` between settled turns before rotating a thread for context capacity. Its maintenance requests are accounted for separately from proof turns; failed compaction retains the existing fresh-thread recovery. Skill research keeps Codex's own automatic compaction behavior. Ordinary peer-status notices in the legacy cooperative path also use advisory native history; assignment changes and other effective instructions keep their steering contract.

Historical teams use `thread/inject_items` for ordinary advisory updates and `turn/steer` for effective amendments with the existing paid-request settlement fence. Native teams deliver through Codex's mailbox and attributed input. Queue-only delivery never starts an idle turn; acceptance transfers queue ownership and is not a read receipt. An amendment uses exact-turn steering so a late notification cannot start another writer. Uncertain delivery after worker loss stays explicitly uncertain.

New team runs use the separately built [Codex AgentControl backend](../scripts/codex-backend/README.md). Official `spawn_agent`, `send_message`, `followup_task`, `list_agents`, `wait_agent` and `interrupt_agent` handlers stay installed. The adapter connects them over stdio to TheoremOS's isolated writer lifecycle. The host prepares a separate process and worktree before the first child model request; trusted bootstrap preserves native tree identity, captured instructions, parent lineage and native fork history. Workspace relocation revokes the parent's writable worktree and permits the destination isolated workspace while retaining other restrictions. Per-worker provider settings stay local to the worker process.

Codex's generic root/subagent role messages are deliberately suppressed: their defaults assume a shared working directory and allow recursive child teams. TheoremOS supplies the actual flat-team identities, isolated workspace permissions and native usage guidance through the pinned context instead. This does not remove native tool descriptions. Deferred mailbox preemption preserves delivery at the next model boundary after the current response and tools settle; it does not require a host coordination acknowledgment.

Native team sessions also set Codex's existing `features.multi_agent_v2.multi_agent_mode_hint_text`. Lead receives explicit authorization to proactively delegate useful complementary work; members receive a flat-team policy that permits messages and forbids further dispatch or peer interruption. This replaces the default explicit-request-only mode message emitted at `high` effort, which otherwise follows the host's team authorization. The override is recorded with the runtime configuration and reapplied on new and resumed writer sessions. Single-agent and historical host-tool sessions keep their existing native mode settings. This adds no dispatch gate, required team size or model-choice override.

Build the pinned backend before starting a new team run. New runs freeze `agentTeam.transport: native-agent-control`, plus the backend executable's real path and digest. `THEOREMOS_CODEX_BACKEND_EXECUTABLE` can select an explicitly built binary; the default is `out/codex-backend/codex`. Startup checks the backend capability endpoint and rejects a stock or incompatible executable. Saved runs without that transport field keep their original host-tool contract. Building does not switch or restart running solves, and no global Codex profile or binary is replaced. Native completion remains separate from stopped-writer source freezing, Lean verification and Lead adoption.

The backend's real-binary [loopback fixture](../scripts/test-codex-backend.ts) covers isolated native spawn, attributed messages, idle queues, cold resume with first-request FIFO mail, full-history fork, loaded-agent listing, mailbox wakeup, changes to a running member's expertise and idle/active interruption. It verifies writer shutdown, checked delivery, adoption and final proof references. Provider responses are fixed local data. Installing the CLI backend does not upgrade an existing Web worker image.

Real installed-Codex tests with local fixed Responses replies cover native shell refusal/correction and concurrent advisory injection, preservation of parallel tool results, and idle injection without model work. These verify transport and lifecycle behavior; no mathematical speedup is inferred from them.

## Agent-organized proof-writing team

For a new Codex run, select the persistent team explicitly:

```sh
bun bin/math.ts run --research-mode skill \
  --skill-delegation team --skill-max-agents 3 \
  --workspace NEW_PROBLEM_WORKSPACE --task-file TASK_FILE \
  --output NEW_RESULT_FILE --build-manifest BUILD_MANIFEST
```

`--skill-max-agents` counts persistent members, including Lead, and accepts 2–8 (CLI default 4): at most one Lead and seven members. An idle or interrupted member retains its place; Lead can use `followup_task` to assign that member a new gap and expertise. Team mode uses one host Lead: `--workers 1 --coordination independent`. These are the Skill defaults; host cooperative coordination, module plans and plan approval cannot be combined with this mode. Native team execution requires the pinned Codex backend. Other harnesses retain their supported host-managed workflows.

Before starting a team, optionally select preferred roles in the Web form or pass a comma-separated list, e.g. `--skill-preferred-profiles researcher,engineer,D011`. Work roles and domain specialties come from the [pinned Skill catalogue](../skills/theoremos-research/references/team-roles.md); a domain ID or its slug is accepted. A preference tells the Lead what expertise you would like considered. It does not reserve seats, start members, restrict other roles, or mark any expertise as used. The run saves these preferences for resume. Leave the list empty for ordinary autonomous selection.

You can also select a released personal Skill or Agent as a source of expertise. The web service checks access and freezes the selected version, including relevant material from its referenced Skills. It uses descriptions, areas, inputs, outputs and examples. To make a source available to an expert, include its citation or link in one of those fields. Legacy steps, execution instructions, module overrides, model and staffing choices are not imported. Put knowledge that you want to reuse from an old instruction block in the description or examples and publish a new version.

For CLI runs, `--skill-expert-cards-file FILE` takes a JSON array with string fields `assetId`, `version`, `digest` (the release's SHA-256), `name`, `summary` and `knowledge`. Lead sees the available names and summaries; a dispatch such as `Profiles: researcher, asset:topology` supplies the selected knowledge to that assignment. The run retains its frozen cards on resume. A card supplies background; it cannot grant tools or certify a claim.

Lead chooses the mathematical decomposition, delegates proof work, changes routes and selects results for adoption. The default Skill guidance uses a flat team working on complementary gaps in the shared proof effort, with alternative-route investigations when useful. Members can discuss findings and interfaces directly; Lead retains dispatch and adoption authority. Each child has an isolated writable worktree, the same pinned Skill and a native thread that persists across assignments. Native collaboration tools carry delegation, instructions and communication. The host provides `theoremos_team` only for mathematical evidence, source handoffs and checked-result adoption. This path is separate from the existing host-cooperative task graph, fixed roles and worker scheduling.

The Skill guides Lead to look for complementary work early; a useful research question can be assigned before a complete proof route or exact helper type is known. Lead uses normal collaboration and research tools at its discretion. There is no outer coordination protocol, tool restriction or coordination-only turn interruption in either transport. Native `send_message` carries findings, route changes and status; native `followup_task` supplies further instructions and `interrupt_agent` stops a member's turn. Lead chooses tasks, methods, when to reassess and team size within capacity, without forced delegation or a required reporting ritual.

Lead and member contexts report remaining run milliseconds, the stage checkpoint and the hard turn limit; continuation recompiles the remaining-time observation. A finite `--max-turn-seconds` remains a hard ceiling. Team turns start handing back control at 80% of that limit: new paid requests stop at the next admission boundary, after the in-flight response and its native tools have finished. For a 300-second turn, the stage checkpoint is at 240 seconds, leaving up to 60 seconds for settlement. A normal native completion is retained; a checkpoint preserves the saved thread and sources. The hard turn deadline, overall deadline and explicit cancellation can still interrupt an unfinished request. Missing usage remains unknown and blocks finite-budget continuation. With no turn limit, no timed stage checkpoint is added.

Team identity is stable: Lead owns the original problem and may also write proofs; each child is a mathematical researcher and Lean proof writer. The pinned Skill's [specialist profiles](../skills/theoremos-research/references/domain-experts.md) supply specialized knowledge: concepts and structures, relevant theories with their conditions, important distinctions and connections to neighboring subjects. Each member chooses its reasoning and proof approach for the assigned question. The catalog contains 100 domain profiles and 24 work or supporting-expertise profiles; these can be combined and are separate from the runtime's agent capacity. Lead provides the question and members read the relevant knowledge sections. The [work profiles](../skills/theoremos-research/references/team-roles.md), including Researcher, Lean Prover, Lean Engineer and Reviewer, describe responsibilities that can accompany a specialization. Lead selects, combines or changes expertise and responsibilities in native spawn and followup messages; no separate `role` or `domain` parameter or host authority is added. Independent review requires a non-producing member and fixed evidence; a role change alone does not make the producing thread independent. This is a Skill collaboration requirement, not an additional host review gate. The host refreshes developer identity and source permissions, while the pinned Skill supplies domain knowledge and collaboration guidance. Each child dispatch starts with a bounded current-assignment section containing its task ID, objective, source and delivery baselines, own prior feedback, peer work and addressed inbox. The inbox cursor advances only after turn-start acknowledgment. See the [source research and prompt design](../research/agent-team-prompts.md).

Start a specialized native `spawn_agent` or `followup_task` message with `Profiles:` followed by comma-separated domain and work-profile IDs or slugs selected for the actual gap. A work profile alone is valid; no domain is selected by default. The child receives the selected profile text and the locations of local reading notes; it can read those notes on demand. When Lead changes the expertise of a running member, the same attributed followup delivers the new profile context to the current turn. The host records the change after the native backend accepts the input; acceptance does not establish that the model used the material. The record includes the pinned Skill digest, requested and loaded IDs, and unresolved names. Historical host-tool runs use the same opening line in `spawn.message` or `assign.message`. Source permissions, agent capacity and proof acceptance do not change.

The Lead charter assigns concrete gaps with a consumer and first usable result, with one owner per active obligation including Lead. While a member owns a gap, Lead advances its consumer or other work; different methods for proving the same target still overlap. Whole-target delegation has one owner while others provide targeted support, integration or review. Alternative routes start with the smallest finding that resolves a specific uncertainty. Members receive the original problem as background to their current assignment and send useful intermediate findings before the complete proof. These are Skill and native role instructions, without a host scheduler or delegation gate.

Native followup retains the member's workspace, thread and draft while the adapter records the latest accepted task instructions and retains earlier instructions in history. It preserves the current profile selection when the message has no new `Profiles:` header, and switches knowledge when an explicit header is supplied. Native submit omits `objectiveRevision`; the host binds the member's current task. Profile records retain exact loaded passage identities; a member can explain a passage's application in its messages or saved research notes. Supplied context, reported knowledge use and checked proof evidence remain distinct. Historical host-tools retain `amend` and optional structured `progress` records, including their objective revisions, work kinds and source-anchor reports, for compatibility.

Members use independent Git object stores; each writer's namespace hides the peer-workspace parent and rebinds only its own workspace. Checked fixed commits and evidence are archived outside writer visibility and imported by exact version for explicit adoption. `inspect` records exposure to a peer delivery, and completed adoption records reuse. These records persist across tasks and accompany later deliveries with the source producer, task and commit. They record explicit source transfers, not complete reasoning independence or independent authorship of reused declarations.

Before a team Lead or member starts Codex, the host runs `check-lean --health` through the same PID/mount isolation, environment, profile and hidden roots. It checks the sealed mapping, lease and pinned compiler without compiling proofs or admitting a model request. Readiness is retained in the isolation receipt and emitted as `lean_environment_ready`; a failure produces structured infrastructure diagnostics and stops that launch. A missing mapping is a namespace visibility fault and does not establish that a host process died. Canonical check-lean returns a nonzero structured error when Lean cannot start; a shell pipeline's final status remains distinct from the compiler result.

Each domain profile also links [collected domain materials](../skills/theoremos-research/references/domain-materials.md). The Skill pins original knowledge notes with source identities, exact reading locations and coverage limits, so these notes are available in the isolated workspace without fetching a book. Full third-party documents and retrieval evidence stay outside the repository; reading an original online follows the run's network policy. The collection supplies domain background and leaves proof approaches to the members. It does not install formal declarations or import literature into the checked theorem catalog.

Collaboration follows useful milestones. Lead keeps the shared route and gap ownership visible through native messages when needed, and assesses findings, probes, blockers and route changes when they affect the next decision. A member messages usable findings and blockers promptly, submits independent helpers once they answer the assignment and returns for checking before expanding its scope. These instructions guide Agent choices without a timed polling loop, forced proof method, task quota or automatic adoption. Waiting is useful when progress depends on an outstanding member result; an empty loaded team alone is not a reason to wait.

The native transport leaves identity, dispatch, instructions, messaging, waiting and interruption to Codex collaboration tools. Its `theoremos_team` host interface exposes only `finish`, `history`, `inspect`, `inspect-research` and `adopt` to Lead; members see only `yield`, `history`, `inspect`, `inspect-research` and `submit`. These are seven distinct mathematical operations. Native `followup_task` resumes a yielded draft or assigns work to a completed member. `list_agents` lists loaded agents; the saved overview retains members and their task/evidence identities after their writer process stops.

Historical host-tool runs retain their role-specific schemas: Lead sees `spawn`, `assign`, `amend`, `finish`, `coordinate`, `resume`, `cancel`, `publish`, `message`, `poll`, `wait`, `history`, `inspect`, `inspect-research`, `adopt` and `stop`; children see `progress`, `message`, `poll`, `wait`, `history`, `inspect`, `inspect-research`, `yield` and `submit`. `budget` and its parameters are available only with an explicitly configured finite token or turn allowance. Descriptions and parameters follow those capabilities, and the host independently rejects unauthorized calls. The pinned [parallel-work reference](../skills/theoremos-research/references/parallel-work.md) documents both transports. Historical spawn/assign queue work and return a task ID. Poll/wait deliver individual arrivals and a durable cursor while other children continue; wait is bounded to 30 seconds. Inspect retrieves checked declaration interfaces, source excerpts, commits and proof evidence so Lead can make an informed adoption decision.

Historical `coordinate` and `publish` remain optional note and summary operations. Saved coordination decisions, observations and presentations remain readable historical records; they do not gate tools, create collaboration stages or schedule turn handoffs.

The historical `message(agentId, message, relatedTaskId?, researchRevision?)` durably saves its event before returning. Native notification is queued asynchronously, so a receiver waiting on its own tool call cannot block all team mutations. The reply distinguishes saved inbox delivery from notification availability; neither confirms reading. Child message events automatically carry the sender's current `sourceTaskId` and `dispatchResearchRevision`, the summary version injected at that sender's dispatch. An explicitly referenced `researchRevision` can be newer; the dispatch revision never asserts that later updates have been read. Native transport uses attributed Codex messages and queue-only mailbox updates instead; accepted mail does not establish that it was read.

Lead/worker dispatch contexts and historical poll/wait share a bounded [overview projection](../src/solver/agentTeamViews.ts): selected members, each member's current/next/recent tasks, recent research/proof references and current integration status. Long objectives, summaries and errors have previews and truncation markers; omission counts and retrieval instructions identify what is not shown. `activity` distinguishes preparing, running, stopping, checking, integrating, paused and idle without claiming mathematical progress. `history(agentId?, offset?, limit?)` returns complete task text and any saved legacy summary, with source/evidence IDs; declaration arrays remain available through checked delivery inspection. The default page limit is 4, maximum 8, with a 256 KiB soft byte limit ending at whole-task boundaries and `nextOffset` pointing to the first unreturned task. A single large task is still returned. Global history uses host-assigned task sequences, stable as new tasks are appended; a task's `historyOffset` indexes its member's history.

Context inboxes contain at most eight event previews. A truncated message and later previews are not acknowledged: `through` remains the last completely shown prefix, and `previewThrough` is explicitly not a receive cursor. Historical poll/wait return at most eight complete events and can stop earlier at a byte limit; their cursor advances only past returned events. Native messages use Codex's attributed mailbox delivery. Long-lived task history, reference indexes and inbox previews remain bounded, with complete content retrievable.

Historical host-tools retain `publish(summary)`, which updates `researchState` with a new revision and publication time and sends members a `research-updated` event. The saved summary is advisory and may describe routes, assumptions, findings and gaps; it is neither a host task graph nor checked mathematical evidence. Native teams use ordinary native messages for these updates and save reproducible notes in RESEARCH.md.

After an executed child task's writer stops, its result records the stable `sourceCommit` and `researchArtifactId`. The artifact contains the task's summary and status, plus the root RESEARCH.md when present; missing notes return `notes:null`. The `researchArtifacts` index exposes artifact ID, producer, task and commit without host storage paths. Any member can use `inspect-research(artifactId, offset?, limit?)` to read paginated saved notes at that fixed commit, using Unicode code point offsets and `nextOffset`. This preserves inspectable counterexamples, literature mappings, calculations and failed routes even when no Lean declaration was submitted. An artifact remains advisory and separate from a checked proof delivery. Historical checkpoints can omit these new fields; the context then has no invented summary or artifact.

Historical host-tools retain `cancel(agentId, taskId, reason?, replacement?)` for withdrawing a task or queuing a replacement, and `stop(agentId)` for retiring a member. A cancellation request and queued replacement do not assert writer shutdown. Native teams use `interrupt_agent` to stop a turn and `followup_task` for further instructions, preserving identity and saved work; a subsequent writer still waits for confirmed shutdown.

For a temporary dependency or Lead decision, a child saves its draft and notes, calls `yield(reason)` and returns. The host confirms writer shutdown before making the task paused. Lead can adopt needed results and use native `followup_task`, or historical `resume(agentId, taskId)`, to continue the task, worktree and native thread. This preserves the original delivery baseline and cumulative task consumption. A normal return still completes the investigation; a submitted proof is checked through the submission path rather than yielding it.

Runs have no token, turn or solving-time budget by default. Without a finite host token or turn allowance, Lead cannot invent local task caps or an integration reserve: the tool omits those capabilities and the host rejects budget requests before creating or queuing a task. Usage accounting continues independently of limits. Older saved task caps and reserves are preserved as history and are not enforced while the host has no finite token or turn allowance. Removing a global token limit on resume requires explicit `--max-total-tokens 0`, because omission retains the old run's value.

Native team tools expose no task-budget or reserve controls. Historical host-tools retain optional `budget:{tokens?,turns?}` on spawn/assign and `budget(leadReserve?, agentId?, taskId?, budget?)` only with an explicitly configured finite host allowance. These replace cumulative local allowances without resetting consumption or resuming paused work. Shared configured limits still govern the whole run. The overview reports observed usage and any saved finite allowances; historical turn limits remain unknown when no host limit was saved. Token caps govern subsequent request admission using observed receipts, so an admitted request may finish beyond a cap. A missing receipt is preserved as unavailable usage.

A child saves its sources, calls submit with exact declarations and returns. Submission and yield also checkpoint at the next unpaid request boundary, after the current paid response and tool group settle; submission enters checking, while yielding retains the task for resume. The host confirms writer shutdown, freezes those bytes and checks the delivery independently. Adopt defaults to Lead and queues integration. Lead saves sources and notes before requesting it; a pending Lead adoption triggers an automatic checkpoint before the next model request. Lead can also call `finish(summary)` after saving to request independent whole-problem checking without relying on a local diagnostic; remaining holes or errors return normal feedback. The paid response and its tools finish and usage settles before confirmed writer shutdown; the host then freezes sources, rechecks and integrates the delivery and continues the saved thread. No token, time or turn allowance is added. Adoption into an idle child also queues and returns immediately; its safe work loop integrates before dispatching the next assignment, allowing native messages and interruption during slow checking. Lead can send the consumer instructions after requesting adoption and inspect the resulting status and feedback. Changed source versions, conflicts or failed checks return feedback. Checked declarations and completed adoptions never replace independent whole-problem acceptance.

In native runs, `send_message` binds the sender to the issuing native thread. Use `/root` for Lead and canonical paths or native IDs for peers. Relative paths follow upstream Codex resolution. Historical host-tool teams retain `message` with `agentId`, their original receipts and deduplication.

For native teams, `result.teamContributions` and `inspect` distinguish checked declarations and their adoption from use in each original proof. The report ties a delivered source version to its transfer into Lead's worktree and to final Lean evidence. Where the evidence permits, it distinguishes a delivered target proof, a direct reference, an indirect reference, and a declaration absent from the proof's references. An older receipt may establish a reference without its depth; missing or ambiguous evidence stays unknown. Member messages are separate advisory records, not proof of adoption or mathematical use.

For long declarations, `inspect` returns a preview for each source change. Pass the same `deliveryId`, its `changeIndex` and `offset: nextOffset` to read the next page at the fixed commit without adopting it. Native spawn evidence distinguishes a fresh thread, a thread with parent history and an unknown history. A parent's inspection before a full-history fork is recorded as possible exposure through the parent. It is neither a direct read by the child nor proof that the source reached the model after context compaction.

Lead and children share the original run's time, turn and token allowances, with cumulative usage saved in host state. Team writers use Linux bubblewrap isolation with separate PID namespaces; host-controlled process identities allow recovery to confirm previous writers stopped before sources are reused. Native runs use the official collaboration handlers with host-backed isolation; historical host-tool teams keep built-in spawn/fork disabled. Native threads, messages, tasks, delivery identities and adoption progress persist on resume. A previously running assignment becomes interrupted and requires an explicit Lead assignment to continue; pending proof checking and adoption use their saved source identities. An unconfirmed writer stop blocks further use of that workspace.

Deferred or rejected source drafts keep their original delivery baseline across assignments, so a corrected helper remains transferable. A stopped child can adopt checked peer work while retaining its own unpublished draft. The host merges against fixed commits, preserves the child's draft and baseline, tracks adopted peer declarations and freshly checks the subsequent combined delivery; the child still names all its own unpublished declarations. Each submit remains limited to 32 declarations; larger host-composed sets are checked in batches, with full-set source-delta and duplicate validation. Conflicts and unconfirmed writer shutdown remain explicit failures. Successful deliveries advance the baseline. Lead adoption completion durably records the next source freeze. If the host exits before whole-proof checking, resume verifies a complete adopted original candidate before admitting another model turn, including when the turn allowance is exhausted.

Child completion and its proof nomination are saved in one transition. A durable submit acknowledged before a crash is also recovered when the final model response was not saved: after confirming writer shutdown, the host freezes and checks the nomination while leaving the interrupted task's status truthful. Historical completion-before-pending checkpoints are repaired only when their fixed source commit is still the current HEAD. The run inspection includes the same bounded runtime overview, fresh aggregate usage, task allowances, pending delivery identities and message provenance; these observations never confer original-problem acceptance.

`--skill-delegation read-only` remains available for bounded advisory investigations through `theoremos_investigate`. It waits for the batch and provides no persistent proof-writing team. Neither mode currently supplies evidence of a mathematical success-rate or efficiency advantage; this stage validates collaboration functionality.

## Skill and host responsibilities

`skills/theoremos-research/SKILL.md` contains stable research methods with references loaded as needed. It has no specific problem answers or universal task graph. The full directory, including references, participates in build and run identity. A run gets its own copy under `.agents/skills/theoremos-research`; the host checks its identity before dispatch and after writer shutdown. Only a host-pinned projection is allowed by source ownership. Legacy runs do not gain a new editable directory.

First installation copies into advisory scratch, checks the complete directory identity, freezes its files and atomically moves it into the final location. An interrupted copy leaves no partially installed skill, so a restart can retry. An existing installed projection with changed bytes is still rejected rather than overwritten.

Precise command examples are generated at `.scratch/theoremos-help.md`, using the existing local-help implementation. References route to this help and existing command `--help`; they do not maintain a second tool registry. Research sources, probes and public notes stay in the existing worktree and scratch storage. Internal chain of thought is neither required nor treated as an artifact.

Skill, team and native-baseline preparation save the Lean project location at `.scratch/worker-project.json`, so `check-lean --worktree` and other shared project tools work without a cooperative assignment. Older cooperative workspaces retain their `COOPERATION.json` fallback. The location is advisory; canonical paths, frozen source policies and environment validation still apply. Team help omits the cooperative-only `research-observe` entry point and uses the team submission interface.

Single Skill research, complete Skill workflows and common-guidance/native comparisons generate optional tool references through the same `researchToolGuide.ts` implementation. It selects the actual projected executable and available corpus, knowledge and library resources. Complete workflows reuse the existing context compiler for tasks, consumers, required feedback, routes, definitions, families and fixed-source review. Workflow guidance and comparison guidance retain distinct purposes. The shared reference does not enable native delegation. The durable writer avoids rewriting unchanged help bytes.

Complete cooperative Skill sessions keep their role, current delivery entry point and exact source scope in session instructions. Stable plan/revision, research, gap, correction and review formats live in the pinned [cooperation reference](../skills/theoremos-research/references/cooperation.md), read by role or current need. Same-thread continuations carry the current assignment, delivery path, contract, inbox, decision requirements and feedback without repeating these formats or prescribing a mathematical route. Pending correction receipt indexes remain mandatory even when their full details exceed the optional context budget. Legacy prompts retain their existing behavior.

Normal turn completion saves source and notes after confirmed writer shutdown. Native resume, request recovery, compaction handling, leases, cumulative usage and the existing dispatch budget remain shared infrastructure. A missing shutdown confirmation quarantines that workspace before any new writer, freeze or acceptance. Unfinished original proofs do not trigger a full original-target compilation after every research turn. A complete candidate still goes through the original strict check and S3 evaluation of **every** frozen original target.

After the frozen research responsibility has actually been dispatched to a native thread, later turns in the same host process use a compact continuation instead of repeating the full task and statement. Current source/check feedback, declaration feedback and saved-work references remain present; the developer source and acceptance rules are unchanged. The first dispatch, a new responsibility/thread, the first dispatch after native context compaction and the first dispatch after a host restart all retain the full task. Both standalone skill and common-guidance comparison paths use this behavior and the existing context byte accounting.

For a single Skill researcher, after confirmed writer shutdown the host durably records `pendingResearchFreeze` before committing sources. It binds the prior HEAD, owned-source digest, problem receipt and environment. Recovery accepts only those unchanged source bytes at the prior HEAD or its single host checkpoint, then completes freezing and check delivery before admitting another model turn. A crash after the source commit but before creating a pending proof check therefore does not require another model turn. An unconfirmed writer stop still quarantines the workspace.

Complete original candidates also acquire a host-owned `pendingProofCheck` after writer shutdown and source freeze, before helper processing or original-target verification. It binds the commit, owned-source digest, problem receipt and environment. Resume completes any pending helper processing and verifies the frozen original candidate before admitting another model turn, even after the turn/token allowance is exhausted. Verification checkpoints retain their normal retry allowance; unavailable verification or host storage errors retain the candidate. A deterministic mathematical rejection clears this pending check and returns its feedback for correction. Persisted successful acceptance can finish pending cleanup without repeating verification; a changed candidate or environment is rejected.

## Independent declaration artifacts

To preserve a reusable helper before the whole problem is solved, the researcher writes `.scratch/declaration-submission.json`, then stops editing and returns:

```json
{
  "declarations": [
    {
      "file": "Submission.lean",
      "name": "Qualified.helper",
      "type": "COMPLETE_CLOSED_LEAN_TYPE"
    }
  ]
}
```

The request accepts up to 32 declarations, with optional descriptions and explicit premises. The host confirms writer shutdown, freezes actual bytes, checks the exact declaration and full type in an isolated projection, and preserves source, environment, checked commit, Lean receipts and references. Other original goals can remain unfinished. A helper depending on their unproved bodies or on new axioms cannot acquire unconditional evidence. Ordinary diagnostics remain advisory.

Successful evidence is stored in the host runtime directory's `declarations.json`; feedback goes to `.scratch/declaration-feedback.json`. Invalid submissions and failed proofs receive correctable feedback. Cancellation, resumable verification checkpoints and unavailable environments retain the request and their distinct failure meaning. Resume rechecks the frozen commit and request bytes before any new model admission, even when the model turn or token budget is exhausted. If that candidate also completes the original problem, the host checks all original targets in the same recovery without another model turn. An independent helper does not mark the original problem accepted.

Small archives keep the v1 manifest. When the next write would exceed 4096 records or 32 MiB, the host preserves the records in content-addressed segments and atomically publishes a v2 root in `declarations.json`. Each segment retains both limits and its run/problem/environment identity; the reader verifies its digest, record count and unique record identities. Segment persistence precedes root replacement, so an interrupted append leaves the previous archive readable and can be retried. The writer can migrate an old v1 count overflow that still fits within 32 MiB; an already oversized legacy file or a single oversized record remains an explicit storage error. Historical records in either format still require fresh consumer checks.

After successful host persistence, consumption is marked completed in host-owned state before removing the request. Recovery can finish either side of that removal without repeating completed verification. A missing request is permitted only for that saved completion phase; changed source or an existing request with changed bytes remains an error. The worker-editable feedback file cannot grant completion. Host evidence-storage failures retain the pending request and propagate as infrastructure failures instead of being consumed as mathematical rejections.

Only explicitly classified submission-content errors and deterministic proof failures produce correctable rejection feedback. Host filesystem, Git, source-integrity and verifier-initialization exceptions propagate with the pending request retained; they do not consume the helper or start a mathematical correction turn.

Within a native team run, an unchanged declaration submission can return its previous deterministic Lean rejection. The host first checks ownership and the proposed patch, then matches the problem, project and baseline trees, declaration list, verifier settings and toolchain. A changed type, dependency or environment triggers a new check. The diagnostic identifies reuse; it does not count as a new Lean receipt. Timeouts and infrastructure failures are retried normally. The cache is local to the running host process.

The existing knowledge interface imports this sidecar alongside legacy cooperative records:

```sh
bun bin/math.ts knowledge build --state RESULT.runtime/state.json \
  --output NEW_CATALOG --report NEW_IMPORT_REPORT
```

Catalog records retain their complete source and provenance, are labeled recorded evidence, and require a fresh check in each consumer. `inspect` and the Web observation types understand the new mode without creating fake tasks, routes or Lead progress. Declaration inspection reports recorded evidence, not fresh acceptance. Library extraction without a legacy canonical record continues to require an explicit commit.
