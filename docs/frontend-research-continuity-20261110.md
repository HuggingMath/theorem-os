# 前端研究流程补全（四）· 2026-11-10

本轮完成产品分析中的八项补充，叠加在 `feat/product-continuity` 已有工作树上。沿用品牌配色、数学排版和可选 Web 服务边界。当前为本地实现，未提交、合并或部署。

| 补充 | 用户入口与行为 |
| --- | --- |
| 题目工作区成为默认入口 | 「我的研究」中有运行的题目卡片，标题和主要操作进入题目工作区。对话、源码和研究控制保留子入口；任务、版本、提交和反馈上下文随导航保留。 |
| 当前阻碍与下一步 | 题目总览聚合当前计划批准、评审、补充意见、交接、依赖、阻碍、议题与认领。优先本人需要处理的人工事项，默认五项，可展开全部；负责人和操作都来自现有记录。已验收题目的历史依赖和失败不冒充当前阻碍。 |
| 人工控制候选投递 | 项目发起者可以选择检查后直接投递，或等待另一位有权限的成员批准。候选检查、人工批准、投递、采纳、执行和完整原题验收分别记录；批准再次核对任务与源码基准，旧版和撤回候选不能绕过门槛。默认沿用直接投递。 |
| 连续候选修订 | 评审人记录具体意见，作者从原候选继续修改并逐条回应。新修订冻结上一版的源码、基准、检查、意见与决定，可直接查看源码差异和修订关系。每版重新检查并经过对应投递流程，旧版不自动变成新版的通过证据。 |
| 人工决定与路线变化 | 路线中的人工决定依据明确任务版本、计划、编辑和检查引用关联节点，展示所引用的基础与结果记录。可对照陈述、前提、推导、依赖及检查，也可在历次尝试中并排阅读。没有精确关联时不推测因果或补造推导。 |
| 计划变化后的人工工作接续 | 变更预览和任务区展示受影响的认领、候选、评审与交接。核对当前任务及源码后，认领可转到新版本，候选可形成新的待检修订，交接重新等待接收人确认，评审可以请求作者提供新候选；也可结束旧工作并保留历史。 |
| Library 试用接回任务提案 | 已检查试用可经明确同意，向指定项目成员共享完整候选、固定成果、参数、缺失前提及回执，进入真实候选检查与评审。原运行已包含所需固定模块时可以投递；缺少模块时，人工批准后准备带固定库的新研究草稿，用户核对配置后启动。 |
| 经过检查的数学调用示例 | 作者在数学成果草稿中补充适用条件、结果和具名 Lean 示例。发布时检查示例的独立目标及证明依赖，并将内容与回执固定到发布版本。读者可以查看公式、源码及回执，将证明体载入任务试用编辑器，调整参数后再检查。 |

历次尝试中的两个路线图使用各自独立的选择状态。选择同一数学任务会同步定位两侧图与推导正文；阅读决定节点后再次选择原任务，也会回到该任务。主路线与比较图之间不会串用焦点。

## 数据与执行边界

新尝试复用现有服务端研究配置冻结流程，带入原 Agent、Skill、数学库的精确版本与本次成果。准备时核对完整模块和研究方案能否复原；不向原运行静默安装新模块。候选仅含辅助文件、缺少未发布的多文件依赖或超出新研究输入限制时，会保留原草稿并说明需要补齐的内容。

Library 私人试用证据只有在明确同意后才共享到所选项目。项目成员在候选评审中查看共享证据，仍受项目及运行权限约束。历史修订、接续记录和评论沿用账号删除清理。结束已投递工作的记录不表示撤回已经执行的操作。

候选通过、调用示例通过和局部任务通过都不代表完整原题通过。新研究仍需独立验收，CLI 和数学运行时的冻结身份及验收职责保持独立。
