# TheoremOS 评估与改进计划

日期：2026-11-01 · 基线：`main@7a0159a` · 状态：待实施

依据：[Langfuse 阅读报告](langfuse-evaluation-insights-2026-11-01.md)、当前源码及近期提交。本计划只提出后续修改；未重新核验历史运行或调用模型。

**当前判断**

S1 档案、固定 S3 验收、成果流诊断、模块配对实验及语义审阅 scorer 已具备。开发重点应转向用真实案例决定下一步修什么，并验证近期改动的效果。

建议现在投入这一轮工作的理由是：已有工具能够提供分析所需的大部分证据，首批工作只需整理基线和案例；再由观察到的问题决定代码修改，可控制实施范围。最终用同一验收标准下的对照决定策略是否值得采用，也允许得出“保留现状”的结论。

- `b6804b2` 已补充 formalization / informalization 在上报用量达到预算时中断运行中角色；`e4da9e6` 已加入小型限时团队在 Lead 持续未决策时的受限探索。后续先核对适用条件与实际触发，按证据补缺口。
- 原题片段对应、Lean 逐步解释、目标状态及审计展示已落地。语义与解释质量需要校准，不能由引用覆盖或多角色一致推出正确。
- [模块实验指南](../examples/components/EXPERIMENTS.md)仍注明没有完成的模块效果实验，且“后续配置”停留在 Westlake / `high`；[当前 CLI 约定](usage.md)已是 Sub2API / `deepseek-flash` / `max`。

| 优先级 | 修改建议与落点 | 完成标准 |
| --- | --- | --- |

**实施时的具体约束**

1. 第一批只交付基线文档和案例清单。人工整理确有重复劳动后，再考虑在 `scripts/mathematics/` 增加只读汇总脚本，输出案例索引与证据链接，沿用既有统计和验收结果。
2. 指标表保留计数与分母，按验收方法及 `official` 分组；缺失与 unknown 不剔除，零分母为 `null`。同一尝试恢复后去重并更新报告，过期报告不可直接用于比较；成本降低须结合验收结果解释。
3. 闲置探索有等待至少 30 分钟、剩余求解时间至少 30 分钟等门槛；短试跑未触发不能说明机制无效。`critical-path` 同时改变 M3/M5，不能用它归因单个模块。

**测试目的与证据边界**

下表为后续实施时的验证要求。优先复用现有测试，仅为确认的缺口补例；本计划未执行这些测试或效果实验。

| 验证项 | 复用位置 | 要回答的问题 |
| --- | --- | --- |
| 用量与中断回归 | `tests/usageBudget.test.ts`、`tests/formalizationRecovery.test.ts`、`tests/informalization.test.ts` | 累计上报是否重复计数？达到额度后角色是否停止，已保存产物和恢复记账是否仍有效？这不保证服务商计费的硬上限。 |

| 策略效果对照 | 现有 `compare` 的新冻结计划 | M4 变化是否在同题、同预算、同 S3 下改善完整原题结果，成本证据是否足够支持采用？保留全部失败与缺失配对。 |

仅文档改动检查链接和格式；后续修改运行时边界时执行对应聚焦测试与 `bun run build`，确认 CLI 和数学服务仍可独立打包。离线测试通过不作为真实解题收益的结论。
