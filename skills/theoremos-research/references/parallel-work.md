# Organize parallel research when it helps

Delegate only when delegation is exposed and permitted in this session. A useful independent assignment has a concrete question and an inspectable output, such as a source survey with hypothesis mapping, a counterexample search, an exact library declaration, or a separately checked candidate. Account for coordination and duplicated work; do not create tasks solely to keep agents busy.

Give an investigator the original statement and enough definitions and environment context to understand the assigned question. For an independent review, avoid supplying the answer it is expected to endorse. Retain disagreements and check the supporting artifacts before deciding what to integrate.

## Persistent proof-writing team

When the host exposes `theoremos_team`, Lead chooses the decomposition, assignments, route changes and adoption decisions. Children have isolated writable worktrees, the same pinned Skill and their own native threads. A later assignment continues that child's thread and saved sources. Runs have no time, turn or token budget by default; explicitly configured host limits apply to all agents together. The host enforces source ownership, process isolation, persistence and independent proof checks.

### Choose the run's transport

In a native AgentControl run, use the exposed native `spawn_agent`, `followup_task`, `send_message`, `list_agents`, `wait_agent` and `interrupt_agent` tools for collaboration. The host's `theoremos_team` then advertises only mathematical operations such as task amendment, progress, yield, submission, inspection and adoption. Native tools own canonical agent paths, native sender identity and mailbox wake behavior; do not reproduce them through a dynamic tool. Use absolute paths such as `/root` for Lead and `/root/NAME` for peers, or native thread IDs. Workspace member IDs in mathematical host operations are shown separately in team observations.

Native followup steers a busy member within its current task, resumes a yielded task with the same identity and draft, and creates a new task for a member whose last task has finished. Messages and followups do not implicitly amend the effective objective of a running or yielded task; use `amend` for that change. Native interruption retains membership and saved work. Members can message peers but only Lead dispatches or interrupts members. A native completed result remains advisory; save and `submit` for independent mathematical checking.

The `spawn`, `assign`, `message`, `poll`, `wait`, `resume` and `stop` spellings in the remaining historical host-tools examples apply only when the run advertises those `theoremos_team` operations. In native mode use the corresponding native operation above. Put selected profiles and the self-contained assignment in the native tool's `message` field. Native mailbox acceptance is not a read receipt, and an unloaded member is not proof completion.

### Start and reassess

Use the [Lead charter](team-roles.md#lead--organize-and-connect-the-work) for the opening collaboration decision, then record it through the current transport. Use native `spawn_agent` in native mode; in historical host-tools mode use `theoremos_team` with `operation: "spawn"`, a new `agentId` and a self-contained `message`. Start extended proof work after that choice. A catalogue survey is not a prerequisite.

An accepted dispatch records the decision to delegate, not a finding that the work is complementary. When no useful assignment is ready, call `coordinate` with `decision: "defer"`, a concrete `reason` and a specific `nextStep` whose result will inform reconsideration. For example, inspect an unresolved definition or run the local probe needed to identify a usable question. Do not postpone this decision until the entire proof is understood. A progress message or private note alone does not record this host decision.

The host presents the current `coordination` observation and research stage in Lead context. An unanswered opening decision, completed deferred step, unpublished assignment change or new addressed update can trigger a reminder after the current response and its tools finish. A native coordination reminder continues the existing session; source handoffs still require confirmed writer shutdown. An unresolved decision remains pending after its reminder; presentation is neither a decision nor an inbox acknowledgment. This imposes no token, time or turn allowance. Publish the route and ownership after dispatch or an objective change. After reviewing an update, dispatch work or record `coordinate` with `decision: "continue"`, its `reason` and your `nextStep`; publish any resulting change. Lead chooses the route, questions and number of members; do not fill every available slot without useful work.

When the host reports a finite remaining run allowance or hard turn deadline, plan investigations, save sources and RESEARCH.md, and return for checking or handoff before cutoff. An explicitly configured hard native-turn limit can interrupt an unfinished provider request even when the overall run has time left. Save useful partial work at natural milestones; use a member's `yield` when a dependency calls for a resumable handoff.

Organize a flat team around complementary gaps in the current proof effort. Direct discussion between members can clarify interfaces or challenge assumptions without passing every message through Lead. A whole-problem alternative or independent reconstruction can be useful, but state why that overlap matters and what evidence will inform the route decision. Do not label identical original-target assignments complementary merely because different agents received them. Lead remains responsible for assignments, shared route changes and formal adoption, while each member chooses its mathematical approach.

For `message`, `agentId` always names the recipient. The host supplies the sender from the current session. A member reports to Lead with `{"operation":"message","agentId":"lead","message":"..."}`; use the other member's ID for a peer. Self-addressed messages are rejected with corrective feedback. A successful response echoes `from` and `to`; check the recipient when correcting a rejected call.

### Identity and assignments

The durable identities are Lead and mathematical researchers who can write Lean. Lead may research and prove as well as coordinate. A member's `agentId`, workspace and thread persist; its expertise and work focus come from the current assignment and can change. Match [domain knowledge](domain-experts.md) to the actual missing concept, hypothesis or mathematical tool, and [work responsibility](team-roles.md) to the result needed. A broad subject label is not enough reason to load a profile; a Lean interface failure may need a Library Scout or Debugger rather than more domain reading. Read the selected domain section and relevant linked passage. The expert chooses its reasoning and proof approach. Profiles can be combined or reused when each supplies useful knowledge, without adding workers merely to cover roles.

Make the dispatch message self-contained: give the selected profiles, concrete gap or proposed declaration, necessary definitions and known inputs, intended consumer and first usable result. A single helper, useful probe or blocking question can be the first result; do not require all assigned lemmas before communication. Distinguish checked inputs from conjectures and cite delivery or research artifact IDs when available. The host supplies allowed source paths and delivery operations; do not copy Lead's own declaration-submission file protocol into member assignments or invent extra writable files. Profiles go in the message; there is no separate `role` tool parameter. Private scratch paths alone do not transfer their contents.

Choose native `fork_turns` for the assignment. Use `"none"` with a self-contained question when prior conversation is unnecessary, especially for independent reconstruction or review. Use `"all"` when continuing reasoning that genuinely requires the inherited history; it can contain tentative answers, obsolete tool results and Lead's route. Full-history inheritance supplies native provenance, not access to another member's mutable files. The child still receives the host's current assignment, source permissions and its own workspace. Historical host-tools children start without Lead's conversation. For an independent review, choose a member who did not produce the work and provide the fixed claim and required evidence without prescribing the verdict. Record prior exposure rather than claiming independence after an answer-bearing fork.

Put catalogue selections on the first line, for example `Profiles: D006, prover`. Use comma-separated domain IDs, domain slugs or work-profile IDs. The host loads the corresponding profile sections and provides local collected-reading locators from the pinned Skill, including on a resumed thread. Read those linked sections when a concrete missing concept needs them. The context records the Skill digest, selected and loaded profiles, unresolved names and whether a source was injected or is available on demand. Reassignment uses the new selection; earlier specialties remain history. A custom specialty stays in the assignment text. Without a selection, consult the relevant index and clarify useful expertise with Lead.

The task retains `profileEvidence`: the pinned Skill digest and source file, anchor, line range, digests and loading mode. An `available-on-demand` entry identifies readable material; it does not claim its text reached the model. When useful, report a concrete application with `progress.knowledgeUses:[{anchor:"references/domain-experts/FILE.md#HEADING",application:"The relevant assumption or distinction and how it applies here."}]`. This is optional advisory evidence; a loading record or use report does not prove expert contribution or a fresh external-source read.

Lead uses `amend(agentId, taskId, message, reason, workKind?)` when a current objective changes. It preserves the task, draft, thread and old objective, advances `objectiveRevision`, reloads the selected profiles and notifies a running member with the revised assignment. `message` discusses work; it does not revise the objective. Optional `workKind` describes research, proof, independent-reconstruction, review or assembly. For example, changing an independent reconstruction into integration of peer results calls for an amendment to assembly. Retain earlier findings with their original objective revisions.

`inspect` records exposure to a checked peer delivery. Adoption records reuse and its producer, task and commit; that information persists across assignments and is attached to later proof deliveries. Members use independent Git object stores and cannot browse mutable peer workspaces. These records describe explicit transfers, not complete mathematical independence: messages, prior work and the seeded sources also inform reasoning. Do not describe a proof assembled from peer results as an independent reconstruction. Preserve the original authors of reused results even when your delivery also contains their declarations.

On a new assignment, read its task ID, current source/delivery baseline, previous task result, published research summary and addressed inbox. Inspect the relevant source definitions and exact types before extending an inherited derivation. As soon as a concrete claim or application can be checked, save a focused Lean probe and use its result to choose the next step. Current files and host feedback take priority over remembered claims. Retain useful drafts and rejected declarations for correction. If the objective or interface is flawed, send Lead the precise issue, assumptions and supporting example or check; do not silently strengthen hypotheses or switch the shared route. Messages supplement the assignment; `assign` queues more work. Lead uses `cancel` to withdraw a task or queue its replacement while keeping the member, and `stop` to retire the member. Cancellation does not confirm writer shutdown; replacement waits for shutdown in that workspace and thread.

Communicate a useful reduction, blocking question or contradictory finding as soon as it affects another member's work. Include enough argument, exact declaration/type, assumptions and evidence references for the recipient to assess it. Optional `relatedTaskId` and `researchRevision` identify the task or published summary being discussed. The host records the sender's `sourceTaskId` and the research revision injected at its dispatch; that revision does not assert it has read later updates. A successful message call confirms durable inbox storage. Native notification is queued separately and is not a read acknowledgment. A local Lean check is advisory; use `submit` for transferable formal evidence. Lead can continue independent research while children work and use `wait` when progress depends on their arrivals.

### Keep findings moving

Apply the [Lead charter](team-roles.md#lead--organize-and-connect-the-work) when publishing ownership, receiving findings or deciding adoption. Assess native messages and available results (the durable inbox in historical host-tools mode) at the charter's research milestones. When the first usable result is ready, handle its submission, checking and adoption before requesting optional extensions. Use `amend` to change an effective objective; a message alone does not release an existing responsibility.

A member reports the first usable finding, local probe result or blocker when it can affect another member's work, including on a whole-target assignment. Send the exact claim, assumptions, argument or diagnostic and remaining uncertainty, and save reproducible notes. Once independent Lean declarations answer the assignment, message Lead, save source and RESEARCH.md, call `submit` and return for host checking before expanding into a peer's gap. Remaining holes in unrelated original targets do not prevent a helper delivery. If a host command fails, send its command, diagnostic and any documented fallback result; distinguish infrastructure failure from a failed mathematical argument. Lead can arrange the next assignment once the result has entered the checking and handoff path.

Use `progress` to publish a finding, probe result, blocker or route change against the running task. Supply the current `objectiveRevision`, `kind` and a self-contained `summary`, with `nextStep`, `evidenceRefs` and `knowledgeUses` when useful. Choose an exact first probe or question that can change the next decision, and report its result when it becomes useful to someone else. Progress is saved with the current objective revision and sent to Lead; private transcript commentary is not a shared progress record. Tool activity and reported mathematical progress remain separate observations, and progress does not grant proof acceptance.

Use these milestones to keep collaboration connected; no fixed message count, polling interval or mandatory proof method is imposed.

### Handoff and limits

When a peer dependency or Lead decision blocks the current task, save the draft and RESEARCH.md, call `yield(reason)` and return. The acknowledgment requests writer shutdown; the task becomes `paused` only after shutdown is confirmed. Lead may adopt a needed checked result and `resume(agentId, taskId)` to continue the same task, source baseline and thread. A normal return still finishes the investigation; use `yield` when the existing task should remain open. Do not wait indefinitely with an active writer, or call `yield` after requesting a formal submission.

Save before `submit` or `yield`. Both also request an automatic handoff at the next unpaid request boundary. The current paid response and its tool calls settle first; the host then confirms writer shutdown. Submission enters declaration checking; yielding retains the task for resume. No further model request is needed to poll this handoff.

When all original proofs are saved, Lead can call `finish(summary)` to request whole-problem checking even when a local diagnostic could not start. Return after the call; the host also hands off before the next request, freezes actual sources and independently checks every original target. This is a submission request, not acceptance. Remaining holes or failed checks return ordinary feedback for continued work.

Do not set task budgets or a Lead reserve by default. If the host has no finite token or turn limit, `budget` and the budget parameters are absent from the tool interface; continue useful work without creating local quotas. Report observed usage as usage, without turning it into a stopping rule.

Only when the host explicitly configures a finite token or turn allowance are budget controls available: Lead may give `spawn`/`assign` an optional `budget:{tokens?,turns?}` and use `budget` to replace a live task's allowance or `leadReserve:{tokens?,turns?}`. Task consumption is cumulative across yields and resumes; changing the allowance does not reset it. Supplied allowance/reserve objects replace their previous values, so include dimensions you intend to retain. An empty task allowance removes its local caps; an empty reserve releases the reserve. When all host token and turn limits are removed, older task caps and reserves remain in history but are not enforced. Budget changes do not resume a paused task: Lead explicitly resumes it after the limit or dependency is resolved. Token limits govern later request admission from observed receipts; an admitted request can finish beyond the allowance, and unavailable usage remains explicit.

Save reproducible arguments and exact code in RESEARCH.md and owned source files. In the final summary, identify what was established or remains open, the declarations or evidence to inspect, the precise blocker if any, and a useful next step. Do not report a rejected delivery as checked or a finished investigation as an accepted proof. No fixed report template or role acknowledgment is required.

### Shared research and saved findings

Lead can `publish` a concise current research summary describing the useful route, established findings with references, working assumptions, decisive negative evidence and remaining gaps. Choose the content needed by the team; no fixed report format is required. Publishing advances its revision, saves its publication time and sends members a `research-updated` event. The latest summary is included in member contexts and `poll`/`wait` snapshots with `advisory:true`. It conveys the team's current judgment and grants no proof acceptance. Members send corrections or disagreements directly to the relevant peers and Lead; Lead decides how to update the shared route and summary.

Contexts and `poll`/`wait` use a bounded overview: current/next/recent tasks and recent references, task-text previews and omission counts. Member `activity` distinguishes preparing, running, stopping, checking, integrating, paused and idle; these are execution observations, not mathematical progress. The budget projection reports shared remaining allowance, Lead reserve and, for a current member, its cumulative task use. Use `history` to page complete task objectives, summaries and errors and read the full current research summary. A task's `historyOffset` is its offset within that member's history. Without `agentId`, history follows the host's stable global task sequence. Follow `nextOffset` until null; the default limit is 4 and maximum 8, with a byte limit stopping at whole-task boundaries. Declaration arrays are omitted; use `inspect` for checked proof interfaces.

Context inbox events can be previews. `textTruncated` means the body remains unread; `previewThrough` is not a receive cursor. Use `poll(after: through)` to obtain complete messages. `poll`/`wait` return at most 8 complete events and can return fewer to stay within their byte allowance; continue from their returned cursor. Older omitted task and reference records remain in the archive and are discoverable through task history and evidence IDs.

After an executed task's writer has stopped, the host saves a stable `sourceCommit` and `researchArtifactId`. The artifact contains its summary and task status, plus RESEARCH.md when present; absent notes are reported explicitly. These references remain discoverable in task results and the team's `researchArtifacts` index when the producer takes another assignment. Use `inspect-research` with the artifact ID to read the saved findings at that fixed commit, following pagination until complete. This is the path for a source survey, counterexample argument, failed route or useful calculation without a formal Lean delivery. Refer to its hypotheses and evidence when using it; a stored artifact is advisory even if its note reports a successful local check. Inspect checked proof declarations separately with `inspect`.

Use the tool's `operation` field:

| Operation | Caller | Arguments and result |
| --- | --- | --- |
| `coordinate` | Lead | `decision` (`defer` or `continue`), `reason`, `nextStep`: save the collaboration choice and the next bounded research step. Delegation is recorded by `spawn`/`assign`/`resume`. |
| `spawn` | Lead | `agentId`, `message`: create a child and queue its first assignment; returns a task ID. Optional `budget:{tokens?,turns?}` is available only with a finite host allowance. |
| `assign` | Lead | `agentId`, `message`: queue follow-up work for an existing child. Optional `budget:{tokens?,turns?}` is available only with a finite host allowance. |
| `amend` | Lead | `agentId`, `taskId`, `message`, `reason`, optional `workKind`: revise a queued, running or paused objective without replacing the task or draft. `spawn`/`assign` also accept optional `workKind`. |
| `progress` | Child | `objectiveRevision`, `kind` (`finding`, `probe`, `blocker`, `route`), `summary`, optional `nextStep`, `evidenceRefs`, `knowledgeUses`: save advisory progress against the current objective revision and notify Lead. |
| `finish` | Lead | `summary`: after saving, request writer shutdown and independent checking of all original targets. |
| `budget` | Lead, finite host allowance only | Optional `leadReserve:{tokens?,turns?}` and/or the complete `agentId`, `taskId`, `budget:{tokens?,turns?}` group: replace the reserve or that task's cumulative allowance without resuming it. |
| `yield` | Child | `reason`: save and return for confirmed writer shutdown, pausing the current task while retaining its identity and drafts. |
| `resume` | Lead | `agentId`, `taskId`: queue a paused task again with the same identity and cumulative allowance. |
| `history` | Any member | Optional `agentId`, `offset`, `limit` (default 4, maximum 8): page complete task text, source/evidence references and the full current advisory research summary. |
| `cancel` | Lead | `agentId`, `taskId`, optional `reason` and `replacement`: cancel a queued task or request a running task's shutdown; an optional replacement message queues a new task for the same member. |
| `publish` | Lead | `summary`: update the versioned advisory team research summary and notify members. |
| `message` | Any member | `agentId` is the recipient, `message`, optional `relatedTaskId` and `researchRevision`: durably save an advisory message and return `from`/`to`; native notification is queued separately. Self-addressed messages are rejected. |
| `poll` | Any member | Optional `after` cursor: receive addressed events, the advisory research summary, worker/task results, research artifact references, delivery IDs and adoption status immediately. |
| `wait` | Any member | `after`, optional `timeoutMs` from 1 to 30000: wait for addressed events, then return the same snapshot as `poll`. |
| `inspect` | Any member | `deliveryId`: read a checked delivery's exact declarations, provenance, commit, source digest, imports, source excerpts and proof evidence; records the caller's exposure to this delivery. Excerpts report truncation. |
| `inspect-research` | Any member | `artifactId`, optional `offset` and `limit` in Unicode code points: read a page of saved research notes at their fixed commit; follow `nextOffset` until complete. |
| `submit` | Child | `summary`, `declarations`: nominate the current assignment's exact declarations for checking after returning. |
| `adopt` | Lead | `deliveryId`, optional `targetId` (default `lead`): queue checked integration into Lead or an idle child; returns before integration completes. |
| `stop` | Lead | `agentId`: prevent further assignments and request interruption of an active child; shutdown finishes asynchronously. |

`spawn` and `assign` queue work without waiting for its completion. Receive results through `poll` or `wait`, passing the cursor returned by either receive operation as `after` on the next one. Each result can arrive while other children continue. Messages and completion summaries are advisory. Use `inspect` to assess a proof delivery before deciding whether to adopt it. A saved result is available even after its producer receives another assignment.

A child submitting Lean work supplies 1–32 declarations, each with `file`, fully qualified `name` and complete closed `type`; optional `description` and explicit `premises` preserve its interface. After an amendment, include the current `objectiveRevision` in `submit`; stale revisions are rejected. List every changed declaration in the delivery. Frozen original declarations keep their names, statements, hypotheses and permitted source structure. New independent helper declarations are allowed inside editable owned Lean files; keeping original proof edits within their permitted bodies does not forbid these additions. Helpers cannot depend on unfinished original proofs or new axioms. Scratch experiments remain under the documented scratch paths; put transferable helper declarations in an editable owned file before nomination. Save sources and research notes, call `submit`, then return. Its `pending-writer-stop` response records the request; it does not assert that checking passed. The host confirms shutdown, freezes actual source bytes and checks the submitted declarations before publishing a delivery ID. Read failures from the task/event feedback and correct them through a later assignment. A deterministic source-policy failure preserves the invalid draft and clears that rejected nomination so the same member can repair it; invalid source bytes do not create a checked commit or research artifact. If the host identifies a file outside ownership, repair it in your own worktree and nominate only permitted source paths. Historical pending infrastructure checks retain their separate retry path.

Draft sources from a deferred or rejected delivery remain part of the next submission. List their changed declarations as well as the new corrections; only a successful delivery advances this source baseline. A stopped child may receive a checked peer adoption while retaining its own unfinished draft. The host preserves that draft and its delivery baseline, rechecks the integration and reports conflicts. Later submissions still list all of the child's own unpublished changes; adopted peer declarations are already tracked by the host and need not be manually resubmitted as new work.

For adoption into Lead, save current sources and RESEARCH.md, call `adopt` and return. A queued adoption also triggers an automatic handoff before the next model request: the current paid response and its tools finish, the writer stops, and only then does the host freeze sources, recheck and integrate the selected delivery. It continues the saved Lead thread with feedback; no polling for this integration or additional request is needed before the handoff. This scheduling step imposes no token, time or turn allowance. Adoption into a child requires that target to be idle, with no active writer, and returns a queued request. The host completes pending integration before dispatching its follow-up work, so Lead may queue the consumer assignment after requesting adoption. Read the adoption status and feedback before treating the declarations as available. Messages and cancellation can continue while the host checks that adoption. A conflict or failed recheck is reported to Lead. Do not copy a peer's mutable files or edit another worktree or host state to bypass this protocol.

Keep organizing useful work while children are active. On host recovery, an interrupted assignment retains its sources and thread but needs an explicit new assignment to continue. Pending checking and adoption retain their saved identities. An unconfirmed writer stop prevents further writing or acceptance in that workspace.

A checked local delivery or completed adoption does not establish the original problem. The host independently checks every frozen original target before whole-problem acceptance.

## Other delegation modes

When only `theoremos_investigate` is exposed, use its bounded `questions` array for read-only investigations. That call waits for all results; investigators do not retain proof-writing assignments. The primary researcher integrates any useful findings within its own source permissions.

Without a supported team interface, use read-only investigations or separately isolated candidate workspaces within the actual host capability. Do not grant broader permissions, edit run state or treat a completion message as proof acceptance. An unavailable child tool is not a reason to fabricate a parallel workflow. Historical host-tools and read-only investigation modes keep built-in spawn/fork disabled; native AgentControl mode uses its explicitly exposed native collaboration tools.
