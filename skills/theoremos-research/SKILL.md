# TheoremOS research

Work toward the frozen original statement. Choose the mathematical approach, research decomposition and next experiment from the evidence available. Read the actual owned sources and relevant definitions early. Once a claim or library application can be tested, save a focused Lean probe and inspect its result before building more work on it.

The current host assignment fixes your role, owned paths and available tools. Use native editing, shell and search within its permissions; delegation also requires an exposed, permitted tool. Read `.scratch/theoremos-help.md` for this run's commands and delivery interface.

When the host selects native AgentControl, use the exposed native collaboration tools for spawn, followup, message, wait, listing and interruption. `theoremos_team` then handles mathematical tasks, source handoffs and checked-result adoption. Historical `theoremos_team` transport examples below apply only when those operations are advertised. Follow the run's current transport and target identities.

When `theoremos_team` is exposed, Lead organizes a flat team using the [Lead charter](references/team-roles.md#lead--organize-and-connect-the-work), which the host injects into Lead's stable instructions at startup and continuation. It governs the opening decision, complementary ownership and use of results. Follow [parallel-work.md](references/parallel-work.md) for the current operation contracts.

Choose expertise for the specific missing concept, assumption or formal interface. Begin the assignment with `Profiles: D006, prover`, replacing the example with relevant domain IDs or slugs and work profiles. The host loads their core knowledge and locators for reading on demand; custom expertise can be described in the assignment. Give the concrete gap, known inputs, intended consumer and first useful result. The member chooses its proof approach. Choose inherited history to suit the task, following [parallel-work.md](references/parallel-work.md#identity-and-assignments).

Members send the first usable finding, probe result or blocker through native messages or `progress`, with the exact claim or question, assumptions and available evidence. Do not wait for every subgoal before reporting. Private reasoning is not a team update. These are research milestones, without fixed polling intervals, message counts or task quotas.

Use `amend` for a changed task objective, retaining its draft and history. Name the specific loaded knowledge and its application when relevant; loading evidence and reported use are distinct. Inspection and adoption retain peer-result provenance; describe reused and assembled proofs accurately. Read [parallel-work.md](references/parallel-work.md) for the operation contracts.

Frozen original declarations retain their statements, hypotheses and permitted source structure. Add independent helpers inside the exact editable Lean paths supplied by the host; the same filename in different members' worktrees denotes separate copies. Lead describes mathematical work while the host supplies file and delivery rules. Keep scratch experiments under the documented scratch paths; transfer useful helpers through the current owned-file delivery interface. Helpers may be checked while unrelated original goals remain open, but cannot depend on those holes or new axioms.

Members write in their own workspaces and retain their native threads for follow-up assignments. When a helper answers the assignment, save sources and RESEARCH.md, message Lead, `submit` and return for host checking. A dependency can instead require saving and `yield` so Lead can arrange adoption and resume the same task. Lead saves before adoption or `finish`. These handoffs stop writing before independent checking. Work without budgets by default: do not invent task quotas or a Lead reserve. Only allocate an explicitly configured finite run allowance, and respect any actual host deadline.

Use these references when the work calls for them:

- [Literature](references/literature.md): when a proof idea or missing result may be found in external sources.
- [Lean work](references/lean.md): when finding, testing or delivering formal declarations.
- [Continuation](references/continuation.md): when starting from saved work or preparing durable research artifacts.
- [Cooperation](references/cooperation.md): when the host uses its cooperative task-graph workflow; read the shared rules and relevant assignment, review or feedback section.
- [HuggingMath](references/huggingmath.md): when asked to export a completed result or transfer it into private Hub drafts.
- [Parallel work](references/parallel-work.md): when `theoremos_team` is exposed or an independent investigation can usefully run alongside the current task.
- [Domain experts](references/domain-experts.md): when a question calls for specialized mathematical knowledge. The subject index and subject-boundary table route to theories, concrete examples, counterexamples and connections with neighboring domains; read the selected profile and its relevant reading notes.
- [Domain materials](references/domain-materials.md): when a specialist needs subject background. Collected author and university sources have precise reading locations, original knowledge summaries and coverage limits; each domain profile links its relevant notes.
- [Team roles](references/team-roles.md): when choosing work responsibilities such as Researcher, Lean Prover, Engineer or Reviewer, or supporting expertise. Combine these with domain knowledge as useful and read only the selected details.

Keep reproducible sources, citations and concise research notes that connect established results, assumptions and remaining gaps to their evidence. Save enough for another session to continue without a private conversation.

The host independently checks fixed sources and environment for proof acceptance and reusable-library admission. Local diagnostics, review verdicts, completion messages and historical receipts do not grant current acceptance. Deliver through the current assignment and use its feedback.
